# 不停机更新与任务恢复（单机）

映芽的正式发布使用固定 Nginx 入口、可替换的 API 进程，以及按用户独立运行的
Worker。所有服务均运行在具名 tmux 会话中。开发用的 `dev-service.sh` 默认保持
`standalone` 模式，`backend:service:restart` **不是**正式发布命令。

## 更新时的行为

- API 更新不会结束 Worker、Codex app-server、沙箱网关或正在渲染的视频。
- 新旧 API 共用持久化的 Worker 路由。Worker 独立监听本机动态端口，内部模型和
  语音调用始终回到自己的端口，不依赖正在被替换的 API。
- 目标版本变更后，旧 Worker 完成当前 Agent 回合及已开始的渲染，停止领取后续
  Agent 任务。期间接收的新 Agent、渲染请求先落盘，再由新 Worker 执行。
- 交接单位是**用户**：同一用户的所有在途工作完成后交接，其他用户可以独立更新。
  不承诺同一用户的新任务在旧任务完成前就开始执行。
- SSE 连接可能短暂重连。客户端沿用事件序号补读，登录会话、预览授权、任务 ID
  不随 API 切换丢失；旧版带哈希的 `/static/` 文件保留。
- API 的 SIGINT/SIGTERM/SIGHUP 等待有限请求完成后退出。Worker 的同类信号触发
  排空，**没有到时强杀**。停止按钮的取消语义与发布排空相互独立。

## 安装和首次切换

需要 Linux、本机文件系统、tmux、Nginx、Python 3、Rust/Node 构建工具，以及原有
Bubblewrap、FFmpeg、Codex 登录和 HyperFrames 浏览器。使用普通仓库用户运行，
不用 systemd，也不修改系统 Nginx 配置。入口默认只监听 `127.0.0.1:8797`，外部
HTTPS 网关继续代理到此端口。

在仓库根目录执行：

```bash
npm run release:build -- 20260911-01
npm run release:activate -- 20260911-01
npm run release:status
```

默认目录：

| 内容 | 路径 |
| --- | --- |
| 不可变版本、各自的 node_modules、前端构建及二进制 | `.runtime/releases/<版本>/` |
| 账号与项目数据 | `data/` |
| Worker 路由、版本目标、预览授权、进程锁 | `data/deployment/` |
| Nginx 独立配置、日志及旧版静态资源 | `data/deployment/` |
| 宿主凭据及浏览器缓存 | `.runtime/` |
| 服务配置文件 | `.env`，通过 `YINGYA_ENV_FILE` 显式读取 |

可通过 `--data`、`--runtime`、`--releases`、`--env-file`、`--port` 覆盖；同一个部署
的所有命令必须使用一致的路径和入口端口。路径不能包含 Nginx 配置控制字符。
脚本会保留调用环境（包括代理），本机健康检查和 Worker 转发明确绕过外部代理。
`--runtime` 下的 `codex-home` 是宿主模型登录位置。正式发布固定使用版本目录内
的 Codex 二进制，保证旧任务不会读到更新中的工具；自定义 `YINGYA_CODEX_BIN`
覆盖仍可用于 standalone 开发模式。

**现有旧版单体服务的首次迁移需要等它的任务结束。**旧程序没有独立 Worker，
无法把正在运行的进程内任务搬到新架构。可先在其他端口和隔离数据上验证发布，
待现有任务结束后停止 `yingya-backend`，再让固定入口接管 8797。脚本发现端口
已占用时会退出，不会停止已有服务。之后的日常更新使用上述发布命令即可。

## 日常发布和回滚

`release:build` 复制当前工作区的源码及资源（包含未提交改动），在独立目录执行
依赖安装、类型检查、前端构建和 Rust release 构建。完成后才生成 `release.json`。
重复版本号会被拒绝，不会覆盖旧 Worker 使用中的代码。构建失败可保留目录检查，
下一次使用新的版本号。

`release:activate` 的顺序：

1. 获取部署锁，启动新 API 到独立端口。
2. 检查 `/ready` 和版本标识：静态首页、注册数据库、宿主凭据格式必须可用。
3. 保留静态资源，校验 Nginx 候选配置。
4. 重载固定入口，验证入口确实返回新版本。
5. 发布 Worker 目标版本；旧 Worker 逐用户排空交接。
6. 保存当前版本和前一版本，启动具名 tmux 退出监视任务；等旧 Nginx 工作进程
   的所有连接结束后，才通知旧 API 优雅退出。不会因为一次新版本健康检查成功就
   提前关闭旧连接仍依赖的 API。回滚可复用尚未退出的同版本 API。

健康检查不发起收费模型调用，也不代表所有第三方服务均可用。新 API 就绪检查
失败时不会切换流量或 Worker 目标，失败日志保存在 `data/deployment/<版本>-failed.log`。
切换入口失败时恢复上一份入口配置及 Worker 目标。

回滚复用同一命令，指定已有旧版本：

```bash
npm run release:activate -- 20260911-01
```

回滚期间，正在运行的新版本任务也先完成，再交接回旧版本。不得在发布或回滚中
覆盖运行中的版本目录、删除旧版本依赖，或执行破坏旧版本兼容性的数据库迁移。
当前新增数据字段均有默认值；后续仍须采用“先增加，旧版本退出后再删除”的迁移方式。

## 任务恢复与防重复

本阶段保留现有项目文件格式，使用**用户级内核文件锁 + 同步落盘的任务领取日志**，
避免为了上线而一次性迁移全部项目数据。注册数据库记录 Worker 身份、端口、版本、
心跳；只有拿到对应用户独占锁的 Worker 才能初始化项目、恢复任务及结算中断调用。
API 自身不执行这些恢复操作。该锁会在进程退出时由内核释放，不能根据心跳超时
强行抢占。卡住但仍存活的 Worker 保持所有权，防止两个执行者同时写入。

- Agent 请求在领取前写入 `.yingya/active-turn.json`，保存原始请求 ID、附件、
  反馈、模型和推理设置；先同步日志，再从队列移除，避免领取窗口丢任务。
- 已排队和已领取但尚未派发的任务自动恢复，启动恢复不依赖用户重新打开页面。
- 已派发但结果未知的 Agent 请求保留在队列，要求明确继续/执行；普通新消息不会
  隐式解除这个保护。继续时恢复原 Codex 会话，并先核对已有成果和外部调用记录。
- 用户主动停止的任务不会自动重新启动。已经完成的任务不会重放。
- 崩溃中断的渲染沿用同一任务 ID、版本和参数自动重试，最多 3 次执行尝试；
  已成功写出的完整视频先校验，再补登记，避免再次渲染。没有分帧断点续渲染：
  尚未完成的渲染会从头执行，源文件及已生成素材保留。
- 已发送但结果未知的计费调用按现有保守结算规则记录，不会假定零费用。恢复只
  处理当前用户，其他 Worker 的在途调用不会被误结算。
- 网络中断后的非幂等请求不自动重发。只有 Worker 明确返回“尚未接收”的交接
  响应才可重发写请求；浏览器可用现有 `clientRequestId` 查询/重试 Agent 提交。

任意 Agent 工具都可能包含外部副作用，因此不承诺对任意模型调用、支付或第三方
生成服务实现 exactly-once。结果未知时保留待确认状态，是防止重复调用的边界。

## 查看运行状态

`release:status` 输出当前入口/API 的 tmux 名称和端口，以及 Worker 的 tmux 名称、
监听地址、版本、实例 ID、心跳时间。Worker 会话形如
`yingya-worker-<部署标识>-<用户ID>`，入口/API 会话形如 `yingya-entry-<部署标识>`、
`yingya-api-<部署标识>-<版本>`。

```bash
tmux list-sessions
tmux capture-pane -pt '<会话名>' -S -100
```

Worker 的心跳仅用于诊断。判断存活与交接以实际进程、端口和独占锁为准。不要删除
锁文件：删掉文件会产生另一个 inode，破坏独占保证。不要直接 kill 正在工作中的
Worker 或删除它使用的版本。API 会定期检查已登记用户的 Worker，异常退出后重新
启动并恢复；API 自身意外退出时需重新启动对应 tmux 服务。

## 验证

```bash
cargo test --all-targets
cargo clippy --all-targets -- -D warnings
npm run test:services
npm run test:rolling
```

滚动集成测试使用临时数据、独立 tmux server、动态端口、独立 Nginx 配置及模拟
Codex 协议，不调用真实模型，不修改开发服务。测试覆盖在途任务发布、新任务交接、
真实进程崩溃、原请求恢复、旧会话与预览授权恢复、成片补登记、回滚、候选版本失败、旧静态文件保留，以及
发布期间连续健康请求。

此方案针对**单机应用发布**。不覆盖整机断电期间持续可用、跨机共享文件系统、
数据库破坏性迁移，也不替代数据备份。扩展到多机前需迁移共享存储，并引入可在
写入时校验的租约代次，不能直接把当前文件锁换成超时心跳。
