日期：2026-09-06。状态：M1 已实现并通过自动化、浏览器和真实 Agent 产物验证；M2–M5 尚未实施。

目标：借鉴 OpenDesign 的精准反馈、风格复用和模板组织方式，让映芽的视频修改更准确、同品牌创作更一致、首次创作更容易开始。

## 3. M1：视频时间点圈选反馈

### 用户流程

1. 在草稿视频下点击“标注这一帧”，暂停并固定当前版本、实际播放文件和已解码画面。
2. 在冻结帧上拖出矩形，填写“把这里的字幕放大一点”。支持重新框选、清除选区和取消。
3. 点击“加入修改要求”，输入区出现可移除的反馈卡片，显示缩略图、版本、时间点、描述和截图状态。
4. 通过现有发送按钮提交。任务运行时沿用“排队 / 立即应用”，标注本身不触发生成。
5. 对话历史保留该反馈。点击反馈可查看原截图，并在源视频仍存在时跳转到原版本的时间点。
6. Agent 根据截图和结构化定位修改受影响内容，按现有流程生成下一版草稿。

M1 提供单帧、单矩形和文字；同一次消息可以携带多条反馈，默认最多 8 条。画笔、多区域、实时 HTML 元素选择器在后续扩展。MP4 首版不提供 DOM 元素识别。

### 前端结构

| 建议文件 | 职责 |
| --- | --- |
| `web/src/components/VideoAnnotationEditor.tsx` | 冻结帧、框选、键盘和触摸操作、描述表单 |
| `web/src/components/FeedbackCard.tsx` | 输入区及对话历史中的反馈展示 |
| `web/src/feedback/captureFrame.ts` | 提取解码帧、按视频内容区域计算选区、生成标注图片 |
| `web/src/feedback/geometry.ts` | 坐标转换、边界限制、缩放映射 |
| `web/src/hooks/useFeedbackDraft.ts` | 反馈草稿恢复、上传状态、提交批次 |
| `web/src/storage/draftDatabase.ts` | 从现有附件 hook 提取共用 IndexedDB 连接和事务 |

`AgentWorkspace.tsx` 负责组合、上下文与发送，不继续承载圈选几何和数据库实现。共用 IndexedDB 升级到新版本时保留 `files` store，新增反馈 store，处理旧标签页的 `versionchange` 和升级阻塞；避免多个模块以不同数据库版本各自打开连接。

### 请求与持久化契约

在 `TurnInput`、Rust `AgentTurnRequest`、`QueuedTurn`、`AgentMessage` 及对应 Zod schema 中增加 `feedback: VisualFeedback[]`，缺省为空数组。旧项目无需批量迁移。

示例为拟定契约，路径和哈希由服务端返回：

```json
{
  "id": "<feedback UUID>",
  "kind": "video-frame",
  "versionId": "draft-2",
  "videoPath": ".yingya/versions/draft-2/video.mp4",
  "timeSeconds": 12.4,
  "frameWidth": 1080,
  "frameHeight": 1920,
  "region": { "x": 0.1, "y": 0.72, "width": 0.8, "height": 0.16 },
  "note": "把这里的字幕放大一点",
  "screenshotAssetId": "<server-issued UUID>",
  "screenshotPath": ".yingya/feedback-assets/<asset UUID>.png",
  "screenshotSha256": "<server-computed SHA-256>",
  "createdAt": 1788652800000
}
```

- `region` 相对视频真实画面归一化到 `[0, 1]`，不含播放器黑边、工具栏和 CSS 留白；宽高大于零，矩形必须完全位于画面内。
- 时间与截图在同一次捕获中冻结。切换版本或拖动进度后，旧标注仍绑定原始帧。等待已解码帧有明确超时，不能无限等待暂停视频的下一帧回调。
- `versionId` 与 `videoPath` 都必填；服务端校验视频属于该版本的草稿或导出产物。未能确定版本身份时只开放原有文字时间点反馈。
- `sceneId` 可选，仅当有对应版本的分镜映射时提供；旧版本不得套用当前分镜时间表。
- 截图不保证字幕在语义上被正确识别，因此 `note` 必填。区域数据用于定位，不能解释为自动可编辑的 HTML 节点。
- 草稿截图 Blob 和标注元数据放在同一次 IndexedDB 事务中。已提交反馈以 `messages.json` 为历史事实，`queue.json` 只是待执行投影；避免另建一份可独立修改的反馈历史。
- 截图文件放在项目 `.yingya/feedback-assets/`，不注册为创作素材，避免标注截图被当作视频图片使用。

### 接口与服务端职责

| 接口 | 变更 |
| --- | --- |
| `POST /api/agent-projects/:id/feedback-assets` | 新增 multipart 截图上传；带稳定上传请求 ID，返回资产 ID、相对路径、哈希和图片尺寸 |
| `POST /api/agent-projects/:id/turns` | 接受 `feedback`，与文字、普通附件、队列和优先级一起提交 |
| `GET /api/agent-projects/:id` | 消息和队列中返回结构化反馈，支持刷新恢复 |
| 现有项目文件读取接口 | 读取服务端登记的反馈截图，沿用项目路径边界检查 |

建议新增 `src/feedback.rs`，负责 DTO、归属与坐标校验、截图保存和 Agent 上下文构造；路由在 `src/api.rs` 注册，队列存储仍归 `src/agent_projects.rs`。

上传只接受可解码的 PNG/JPEG，建议最长边不超过 1920 px、单张不超过 4 MiB。服务端检查实际图片内容与尺寸，并使用临时文件加 rename 完成登记。同一上传 ID 和相同内容重试返回同一资产；内容变化返回冲突。服务端根据资产 ID 解析路径，拒绝绝对路径、跨项目引用、目录穿越和逃逸项目目录的符号链接。

提交时验证截图已登记、版本匹配、时间落在源视频时长内，时长探测复用受控 `ffprobe` 调用并缓存。图像和时间相关校验集中在服务端执行，前端提前校验只改善体验。

### Agent 接入

利用 `CodexClient::run_turn` 已有的 `reference_images` 参数，把验证后的反馈截图转换为项目内绝对路径，作为 `localImage` 发送。正常执行与 thread 丢失后的恢复必须复用同一份输入构造结果。

提示词附上反馈 ID、版本、时间、区域和用户描述，明确这些图片是修改标注，不是合成素材。用户反馈作为数据拼接，不允许反馈文本改变项目目录、工具权限或系统契约。

扩展 `yingya-video-agent` 的 Revisions 规则：先读取目标版本及当前源状态，说明影响镜头；旧版本反馈用于说明修改意图，不自动回退当前项目；若无法把旧画面对应到当前内容，应说明差异，不凭空声称定位成功。

### 失败、重试与并发

- UI 展示 `草稿 → 上传中 → 可提交 → 已接受` 和错误状态；“已接受”不等同于修改已完成。
- 截图失败保留选区和文字；用户可重试，或明确选择“仅发送时间点和文字”，后者移除区域和截图字段并使用原有时间点反馈。
- 上传成功但消息提交失败时复用已上传文件。提交超时后，自动重试和手动重试都保留原 `clientRequestId` 和冻结请求体；用户改动内容后才建立新批次。
- 发送期间允许继续编辑下一份草稿；收到接受响应后，仅清理本批次 ID 对应的内容。
- 接受响应之后的列表刷新失败只提示刷新问题，不把提交改为失败，也不重新生成请求 ID。
- 排队撤回保留历史反馈，服务端重启能恢复队列中的截图引用。截图在所关联项目删除时一起删除；M1 不自动清理可能仍由未发送草稿引用的截图。

### 无障碍与窄屏

桌面在现有视频区域进入标注模式；窄屏采用可滚动的单列编辑面板。框选支持 Pointer Events 和 pointer capture。键盘可创建居中默认选区，用方向键移动、Shift 加方向键调整大小，Escape 退出；始终提供文字时间点反馈作为无需精细拖拽的路径。

使用现有 Phosphor 图标、焦点环、语义 token 和减少动效设置。选区同时有编号与边框，错误使用文字说明。320 px 和 390 px 下，描述、取消和加入按钮必须可见且不遮挡输入内容。

### M1 验收标准

1. 横屏、竖屏、方形视频与播放器留黑边时，截图和归一化选区都准确；面板缩放不改变定位。
2. 刷新页面恢复未发送反馈；快速切换项目不串数据；数据库写入失败时明确提示。
3. 模拟上传失败、响应丢失、手动重试和服务端重启，不重复接受同一批消息，不丢失下一批草稿。
4. 排队、撤回和立即应用保持现有语义，反馈随消息一起流转。
5. 用协议测试确认正常执行及 thread 恢复都发送 `localImage`；至少一次真实 Agent 修改使用非文字视觉目标验证图片确实被使用。
6. 通过输入截图修改指定镜头，生成新草稿；旧版本及其截图仍可回看，相关质量检查通过。
7. 旧消息、旧队列、普通附件、原有时间点反馈和版本比较回归通过。

## 4. M2：可复用的视频品牌包

品牌包表达客户视频的视觉与声音规范，建议包含品牌名称、Logo、字体、颜色、字幕样式、安全区、片尾规则和默认音色。用户从“创建设置”选择品牌；提供“保存当前风格为品牌”，保存前预览并允许编辑。

全局可编辑品牌库位于 `AppPaths.app_data/brand-kits/<id>/`，通过配置路径派生；内含 `manifest.json`、`DESIGN.md`、`tokens.css`、`assets/`，维护稳定 ID、修订号和内容哈希。中文视频补充字体回退和字幕规范，不直接搬入通用网页 token 集。

项目创建时复制所选品牌的固定修订到 `.yingya/brand/`，在项目元数据中记录 `brandBinding`。先完成复制和校验，再允许首轮任务启动。全局品牌更新不影响已创建项目；采用新版作为用户明确提交的修改请求处理。

建议接口：`GET/POST /api/brand-kits`、`GET/PATCH /api/brand-kits/:id`；扩展项目创建请求的 `brandKitId`、`brandRevision`。新增 `src/brand_kits.rs`，前端复用当前 `CreationSettings` 和素材选择基础。

冲突顺序：用户当前明确要求 > 项目固定品牌规范 > 模板默认值。项目已选音色优先于品牌默认音色；品牌指定的字体或声音缺失时展示可替代项，不能静默更换。Agent 读取品牌快照后形成项目 `DESIGN.md`，后续版本保存实际采用的设计文件。

验收：同一品牌创建两个不同主题视频时核心风格一致；品牌更新后旧项目不漂移；删除库中品牌不破坏项目副本；没有品牌的旧项目照常运行；上传素材与规则同步进入项目工作区。

## 5. M3：带成片预览的精品模板

首批选择三个已覆盖场景：30 秒产品宣传、60 秒知识讲解、30 秒网页转视频。每个模板都有真实本地预览、适用说明、输入字段、画幅/时长默认值、分镜结构、素材策略、能力需求和验收清单。

建议仓库目录为 `templates/video/<id>/`，包含 `manifest.json`、`BRIEF.md`、`SCENES.json` 和 `preview/`。模板选择只填写创作要求和默认参数；创建项目后仍然先产生制作计划，确认后才创建合成或渲染。预览明确是示例，不作为当前项目已生成结果。

模板预览使用原创、可再分发的受控素材，并在 manifest 记录来源。已批准作为目录内容的小型 MP4/WebP 可纳入版本管理；构建中间文件仍放忽略目录。模板不在用户任务中安装依赖，缺少能力时明确限制或使用已经验证的替代方案。

建议接口：`GET /api/video-templates`、`GET /api/video-templates/:id`；项目创建增加 `templateId`、`templateRevision`、`templateInputs`，服务端校验输入并把固定模板上下文复制到 `.yingya/template/`。记录 `templateBinding`，不另建项目类型。

首页起始建议扩展为少量模板入口；模板详情展示预览和必要输入，再回到统一输入区。颜色、字体交由品牌包覆盖，模板主要约定叙事、节奏和素材需求。

验收：三个模板分别以无品牌和已选品牌完成真实计划→草稿→导出；用户显式画幅、时长和音色优先于模板；参考链接缺失等情况在创建前可理解；模板更新不改变历史项目。

## 6. M4：版本修改摘要与反馈溯源

扩展 `DraftVersion` 的可选字段：`parentVersionId`、`sourceTurnId`、`feedbackIds`、`changeSummary`、`changedSceneIds`、`origin`。`origin` 区分 Agent 修改、手动编辑与恢复；旧版本缺省显示“暂无修改说明”。

队列启动时把本轮身份和反馈 ID 写入应用管理的上下文，Agent 在草稿注册时引用它们。服务端校验来源 ID 和版本归属；变更摘要属于生成说明，实际触及文件由源快照比较佐证，不能用摘要替代源文件检查。

复用当前 `VersionComparison.tsx` 展示修改摘要、反馈截图和检查报告。同步播放作为独立增量：两侧共同的时间范围使用同一控制，时长不同的尾段独立查看；场景变化时不能声称同一时间必然对应同一语义镜头。

确定性恢复另拆任务：在项目任务锁内拒绝活动任务冲突，先验证快照完整性，再备份并恢复受管理源文件，运行检查，最后注册新的恢复版本；保留后续版本。失败保留恢复前源和可重试状态，不能只改 manifest 指针。

验收：可以从新版追溯到具体消息和原始截图；旧版本可读；恢复失败不丢当前源；修改摘要与实际变更方向一致。

## 7. M5：轻量直接编辑与视频专项检查

直接编辑先支持稳定节点 ID 对应的屏幕标题、字幕文案和图片替换。文本旁白变更可能需要重新生成语音和字幕时间，不归入即时文本替换。GSAP 动画属性、时序和任意 CSS 编辑继续通过 Agent 处理。

在源文件契约稳定后新增受控 patch API：请求带 `baseVersionId`、源哈希、稳定节点 ID 和白名单操作；基础版本或源哈希不符时返回冲突。服务端执行 patch、标记 dirty、运行相关检查并注册新草稿。写入源码及资产，避免只在预览 DOM 中生效。撤销和重做也走源文件与版本一致的事务。

视频质量检查分两类：可确定的技术检查继续由程序判定，如素材缺失、字幕越界、音频超出时长；可读性和节奏问题由视觉/语音评审给出带截图与时间点的建议。智能评审建议最多一次检查和一次修复，设超时；未完成显示“未检查”，不能推断通过，也不自动越过制作检查点。

质量报告写入版本目录并绑定源指纹。报告给出检查项、结论、证据、镜头/时间和修复建议；前端使用现有检查报告入口逐步增加摘要。
