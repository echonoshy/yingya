# 视频制作主路径：对比与优化

本次对比基于本机 `/home/lake/workspace/open-design` 的源码，而非线上产品体验。
Yingya 主入口为 `skills/yingya-video-agent/SKILL.md`；讲解视频使用
`skills/faceless-explainer/SKILL.md`，技术制作使用运行环境中已安装的 HyperFrames skills。

## 从 Open Design 借鉴什么

| 参考机制 | 源码位置（相对 open-design 仓库） | Yingya 的取舍 |
| --- | --- | --- |
| Full Plan / Direct Edit 按修改范围分流 | `plugins/_official/scenarios/od-next-strategy/assets/general-orchestration.md` | 新建或方向改变才做方案；局部反馈直接进入受影响场景的修改；仅整理分镜不触发渲染。 |
| Intake / Execution Preflight | 同上 | 方案前检查素材与所需能力，调用前重查可能变化的依赖，避免生成中途才发现音色或素材不可用。 |
| 固定 Design Spec，后续执行沿用 | 同上 | 方案统一审阅视觉、脚本、时长与素材路线；制作沿用 `DESIGN.md`，不在每轮重新问风格。 |
| 时间叙事、动效动机、音画一致性 | `plugins/_official/scenarios/od-next-strategy/assets/task-profiles/hyperframes.md` | 每镜承担明确叙事任务；旁白实测后定时间轴；字幕、转场与画面共用时间依据。 |
| 已验证 scaffold 与异步渲染等待 | `plugins/_official/examples/hyperframes/SKILL.md` 的 OpenDesign integration | 复用 Yingya 已有脚手架、导出任务与轮询能力，主 skill 明确禁止重复初始化和重复启动渲染。 |

Open Design 内部也有不同代际的流程：OD Next 通用编排规定主产物写盘即交付，
不允许生成后质量检查；旧 HyperFrames 集成则强调后台渲染 MP4。
这些是其各自运行模式的约束，不能混合照搬。Yingya 继续保留草稿画面检查、
音画核对、视频验证、不可变版本及审核，也不迁移 OD 的隐藏源码目录、固定配色
或完整 V2 协议体系。

## 已落实的制作流程

1. **读取现状并分流。** 区分新建、局部修改、方向调整、恢复和只读整理；保留用户输入与已有有效产物。
2. **方案与文字分镜一起审阅。** `.yingya/plan.md` 记录目标、视觉、声音、素材路线、输出与假设；根目录 `scenes.json` 提供稳定场景 ID 和预计时间。无需机械创建五份重叠文档，也无需额外风格确认。
3. **按依赖制作。** 沿用脚手架与设计；有旁白时先确定文案，使用已选音色生成并实测音频，再对齐字幕、场景长度和转场；无声视频跳过 TTS。
4. **先解决代表场景，再扩展全片。** 复杂视频先内部检查一个有代表性的场景，降低全片统一返工成本；简单视频直接组装，不增加用户审核点。
5. **统一检查与草稿交付。** 使用 `hyperframes check --snapshots --json`，覆盖结构、运行时、布局、动效和对比度；补足短场景采样并审阅画面与声音，验证视频后封存草稿，最后原子更新 manifest。
6. **按影响范围返修。** 画面修改复用旁白，单镜旁白修改只重生成该段及派生字幕/时间偏移，全局音色改变才重做全部旁白；任何实际内容修改仍需验证新合成和渲染新草稿。
7. **确认后导出。** 从确认版本生成高质量成片，检查已有导出以避免重复任务，产物验证成功后才标记完成。

默认仍是方案和草稿两类审核点。显式的用户授权优先，不增加中间确认。
文字分镜允许作为方案材料先行生成；图片分镜、HTML 合成和视频属于方案批准后的制作。

## 同步修复的执行问题

- 本机 HyperFrames **0.8.20** 的 `check --help` 和已安装 CLI skill 明确说明统一检查覆盖范围；`validate`、`inspect` 已弃用。主 skill、方案确认提示与后端成片预检都改用 `check`，减少分开的浏览器检查。实际耗时收益尚未做前后基准测量。
- 后端预检要求进程成功退出，且完整 JSON 的顶层 `ok` 严格为 `true`。空输出、无效 JSON、缺失 `ok` 或字符串 `"true"` 都不能作为通过凭证。
- 启动时同步完整主 skill 与讲解 specialization，包括嵌套参考文件，避免源码已更新而运行环境缺少新流程。
- 讲解 specialization 移除固定暖白/橙色配色，遵循项目方案；声音、检查和审核归属主流程。

## 后续可独立推进

这些尚未在本次实现，不应描述为已有能力：

- **确定性的制作调度器。** 将场景音频、字幕、素材、合成的依赖与失败恢复从 skill 决策逐步下沉到应用任务记录中。当前改进主要是 Agent 行为约定。
- **完整依赖缓存验证。** 当前后端复用版本报告只核对 `index.html` 与可选 motion sidecar 的指纹；完整资产、字体、子合成变化尚未由后端自动覆盖。本次 skill 已要求发生这些变化时重查，后续应由程序强制验证全部依赖。
- **固定样例评估。** 用无声短片、中文讲解、单镜返修分别记录首个可审阅草稿耗时、生成调用数、重复检查数、字幕同步与返工范围，再根据数据调整流程。
