# Visual direction for editable video

Use this guide when a new film needs a visual approach, when explaining
relationships or data, or when the user asks for PPT/slide-inspired styling.
Existing footage, brand references and approved project design remain the
starting point. A minor correction needs only the affected scene's design.

When there are no usable visuals or the brief leaves the concept unresolved,
use [creative-brief.md](creative-brief.md) to develop the idea and asset routes.
User-supplied reference images are helpful but not required for visual direction.

## Choose what the viewer should understand

Separate **information structure** (sequence, difference, containment, cause)
from **visual treatment** (type, palette, texture, illustration and composition).
A blueprint can explain either a process or a comparison; a process does not
automatically require a blueprint. Select for the audience, viewing format,
actual source material and intended takeaway, not the presence of a keyword.

Read the small [design index](design/index.md), then only the relevant guide
and reference. The bundled selection is a starting point, not a list of allowed
styles or effects. A user reference can justify a different approach. Do not
load every file or combine conflicting style rules merely for variety.

## Make a coherent choice

Choose a visual idea that carries across scenes: for example, one annotated
path connecting successive discoveries, a split composition showing a change,
or an exploded diagram revealing how parts work together. Keep common type,
color and line treatment while varying framing and information layout with
each scene's purpose. Movement should reveal a relationship, move attention or
show a change; changing a palette alone is not a new storytelling approach.

Offer alternatives when requested or when materially different treatments need
a user decision. Otherwise recommend one direction in the existing production
plan with a brief reason. Do not add a style questionnaire or generate preview
images before production authorization. After authorization, test uncertain
directions using [representative-scene.md](representative-scene.md), including
short text-only work whose visual treatment is not yet established.

## Preserve the workflow and user's content

The files under `design/references/` are attributed design material, not
independently invoked skills. Yingya's adaptation guides define how they become
video: original static-image output rules, confirmation flows, page footers,
default themes and browser interaction triggers do not become project rules.
For example, a reference's advice to omit logos does not override required
branding; suggested Latin fonts do not authorize downloading those fonts.

Put the choice and its reason in `.yingya/plan.md`, the scene expression in
`scenes.json`, and the approved shared design in `DESIGN.md`. Keep existing scene
IDs, timing authority, source evidence and manifest phases. Dense reading pages
usually need staged reveals or more scenes; match text load to actual time and
screen size. Preserve locked copy and raise a real duration conflict instead
of silently deleting information.

Customer videos may use paper, bold typography, dark surfaces or expressive
motion when appropriate. The app's UI style is not their visual contract.
For genuine generated images, use the installed image capability only where
the approved treatment needs it; these references do not supply image models,
3D assets or continuous character animation.
